# User-selected notification provider

Each user selects Pushover or ntfy as their notification provider. Exactly one provider receives each newly detected alert. Existing accounts default to Pushover. ntfy users subscribe to their own editable topic, initially `camply-` plus the first seven characters of their user ID, and select ntfy.sh or a custom HTTP(S) server, including a path prefix. The deployment configures a public default subscription URL and optional private publish URL. When the publish URL is absent, it uses the subscription URL. Only the public URL is exposed to users. Each user can optionally override the default with a custom server used for both publishing and subscription. A dropdown offers the configured application server when present, ntfy.sh, or a user-provided server URL. Selecting the configured server follows current deployment defaults; the custom URL input appears only for the user-provided option. An optional bearer token supports protected publishing servers. Secrets and private deployment endpoints are never queued or exposed in profile responses.

Acceptance: copy buttons copy the current public server URL and topic without saving, with clear success/failure feedback and no empty-value copies; the interface shows server and topic separately without a combined Subscription URL section; only the currently selected provider’s settings are visible, and credentials/preferences save together; topics are editable, validated and unique; settings persist in all authentication modes; partial profile updates preserve other settings; suspended/ineligible accounts receive no alerts; both runtimes route summary/direct alerts only to the selected provider. Pending delivery is skipped when the user switches away from its original channel. Validate with mocked HTTP, API, migration, worker and UI tests.

Users can send a test notification through the currently selected provider using unsaved form values. This sends one fixed message without changing saved settings or requiring an active scan/worker. It must respect authentication/eligibility and topic ownership, acknowledge only upstream acceptance, hide private endpoints/tokens in failures, and show pending and result feedback without presenting edited values as already verified.

Review acceptance: changing servers clears the previous server's access token, including partial API updates and draft tests that omit a replacement token. Application defaults remain selectable when the public subscription server is ntfy.sh and publishing uses a private endpoint. New account creation retries generated-topic collisions with a suffix while preserving the user ID and existing topics; explicitly chosen duplicate topics still fail. Save feedback applies only to the submitted settings. The server/topic controls explain subscribing in the ntfy app before testing.
